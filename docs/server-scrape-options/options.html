Chrome, network, and architecture options

Independent choices you can mix: where the browser runs, how traffic exits, how host and schedule connect.

  • Depth tradeoffs
  • Chapters three

Summary

Three independent choices: where Chrome runs, how egress looks, and how host + schedule wire together. Mix one from each column (pairings at the bottom).

Chrome on the server

Yes, fully doable. Prefer full Chrome over slim headless-shell.

A. Chrome / Chromium on a Linux VM

Best realism Install google-chrome-stable or chromium + fonts. Pair with Xvfb for headed-without-monitor.

Pros

  • Closest to laptop Chrome
  • Easier VNC debugging
  • No container sandbox flags required

Cons

  • You manage OS packages
  • ~1–2 GB RAM during scrape

B. Docker with Chrome baked in

More bot-like Extend current slim runtime. Often need --no-sandbox / --disable-dev-shm-usage.

C. Slim headless-shell

Avoid for Tesla Fine for tests; weak against Akamai.

IP & network

Chrome alone is not enough. Prefer changing scrape egress only, not the whole API host.

A. Residential / mobile proxy (Chrome only)

Usually best All on server

textEgress split
Chrome --proxy-server=... --> residential IP --> tesla.com
API clients --------------> your server (datacenter OK)
  • Sticky session for the whole scrape; on block → new session → retry
  • SOCKS auth can be awkward in Chrome (local forwarder if needed)
  • Pool quality matters more than price

B. VPN on the whole host

Ops footguns Feels like a laptop; often breaks SSH/health/API. Prefer policy routing or netns so only Chrome uses VPN.

C. Netns / WireGuard sidecar

Clean split API normal egress; scraper via WG to home or residential exit. More glue, no per-GB bill if home is the exit.

D. Home egress worker

Highest reliability Not all on server Formalize today: home scrapes → import. Best IP + desktop Chrome.

E / F. Multi-VPS IPs · Managed browser API

Multi cloud IPs: still datacenter. Managed browser APIs: high reliability, cost + less control.

Sticky IP per scrape

One residential exit for locations + all detail batches. Don’t rotate mid-run. On hard block: stop → new sticky session → full retry (or retry-failed if partial).

Architecture shapes

1. Host grows a scheduler

One binary: Axum + cron/interval calling run_scrape. Simple deploy; need scrape mutex; Chrome load can jostle API.

bashConfig sketch
SCRAPE_ENABLED=true
SCRAPE_CRON="0 */6 * * *"
SCRAPE_COUNTRY=US
CHROME_PROXY=socks5://user:pass@host:port
SCRAPE_ON_START=false

2. Same machine, two processes

systemd or Compose: host + timed scrape. Crash isolation; scraper-only proxy/VPN.

3. Hybrid import worker

Worker with good IP scrapes → export → import. Prod stays host-only. Lowest Akamai risk; fastest automation.

4. Remote CDP

Server schedules; chromiumoxide connects to home Chrome over Tailscale/WG. Orchestration central; tunnel fragility.

Failure handling (any shape)

  1. Detect block

    HTML responses, high detail-failure rate (partially exists).

  2. Backoff + stop

    Don’t thrash the same IP; mark run incomplete.

  3. Rotate egress

    New sticky session / reconnect VPN.

  4. Retry, then alert

    retry-failed; webhook; optional admin trigger / noVNC.
